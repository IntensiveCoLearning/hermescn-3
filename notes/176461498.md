# 六、第一次真正理解“额度”和“模型能力”是两个问题

```

```

这些问题让自己第一次比较清楚地理解：

```
模型本身
≠
Provider
≠
账户额度
≠
网络连接
```

例如：

### 额度问题

```
HTTP 429
Weekly / Monthly Usage Limit
```

这种情况并不是本地 Hermes 安装有问题，而是账户资源达到上限。

### 上游拥堵

```
temporarily at capacity upstream
```

则表示模型服务当前负载较高。

### 网络问题

例如 GitHub：

```
Failed to connect to github.com:443
```

则属于网络连接问题。

现在开始习惯先判断：

```
到底是哪一层出了问题？
```

再决定修什么，而不是看到一个错误就直接重新安装。

# Day 4｜管理 Session 与多 Agent：理解 Hermes Profile

## 一、今日学习主题

今天主要学习 Hermes Agent 的 **Session 管理、Profile 以及多 Agent 工作方式**。前几天已经完成了 Hermes 的安装、基础操作、真实项目实践以及权限和故障恢复，今天开始进一步理解怎样组织多个独立的 Agent 工作环境，以及怎样让不同任务保持清晰、独立和可持续。

通过今天的实践，我对 Hermes 的认识进一步从“怎么让 Agent 完成任务”，延伸到了“怎么管理 Agent 的工作状态”。

***

## 二、Session 是什么

在使用 Hermes 的过程中，每一次持续的 Agent 工作都会形成一个 Session。

可以简单理解成：

```
一次任务
↓
一个工作过程
↓
一个 Session
```

例如之前在量化项目中的一次完整审计，就会产生一个独立 Session，其中包含这次任务的对话、工具调用以及执行过程。

不同任务可以拥有不同 Session：

```
BTC/ETH 项目审计
        ↓
Session A

策略优化
        ↓
Session B

个人网站改造
        ↓
Session C

README 重构
        ↓
Session D
```

这样做的意义在于，不同任务之间可以保持相对独立，后续需要继续处理某一个任务时，也可以通过历史 Session 找回之前的工作上下文。

这对于长周期项目尤其重要。

***

## 三、为什么需要 Session 管理

在实际使用 Hermes 的过程中，我发现很多任务并不能一次完成。

例如：

```
第一天：
分析项目

第二天：
继续修改

第三天：
测试

第四天：
发现问题重新调整
```

如果每次都重新开始，就需要重复解释：

* 项目背景
* 当前进度
* 已经修改了什么
* 为什么做这些修改
* 之前遇到了哪些问题

Session 管理可以让任务沿着原来的上下文继续推进。

因此可以把 Session 理解成：

> **一个 Agent 任务的“工作现场”。**

而不是简单的聊天记录。

***

# 四、实际使用 Session

在前面的实践中已经接触过类似：

```
Session: 20260828_174643_679974
```

这样的 Session ID。

今天进一步学习 Session 管理相关的方式，例如查看历史 Session、继续最近的任务以及恢复指定 Session。

典型工作模式：

```
当前任务
↓
Session 保存
↓
退出 Hermes
↓
之后重新进入
↓
恢复 Session
↓
继续工作
```

这样可以把一个大型任务拆成多个阶段，而不需要每次都从头开始。

***

# 五、Session 与项目的关系

今天特别认识到一个容易混淆的问题：

```

```

项目是代码和文件。

Session 是围绕项目展开的一段 Agent 工作过程。

例如：

```
D:\Github\btc-eth-trading-system
```

这个项目可以有：

```
Session 1
→ 架构审计

Session 2
→ 策略研究

Session 3
→ 测试修复

Session 4
→ Paper Trading
```

同一个项目可以对应很多不同 Session。

而同一个 Session 更适合聚焦于一个明确任务，避免上下文不断膨胀。

# 六、理解 Profile

如果把 Session 理解成“一次工作”，那么 Profile 更像是：

```

```

→ 日常任务

→ 编程开发

quant
→ 量化研究

research
→ 资料研究
```

这样不同领域的任务可以使用不同环境，减少上下文和工作习惯之间的干扰。

```

这个问题本身并不是故障。

因为第一次创建已经成功，第二次操作只是重复创建，因此 Hermes 正确提示 Profile 已经存在。

这也让我开始意识到：

> 使用 Agent 命令时，需要先判断当前状态，再决定下一步操作。

不能看到错误就认为整个系统出问题了。

# 九、Profile 与工作目录的区别

# 十三、实际学习中的模型问题

今天 Profile 的使用过程中还遇到了一个很现实的问题：

新创建的 Profile 并不会天然拥有和默认 Profile 完全相同的模型配置。

创建 `coder` 后，如果没有配置 Provider 和 Model，启动时会提示：

```
No inference provider is configured yet
```

这说明：

> **Profile 的独立性不仅体现在 Session，也体现在模型配置上。**

也就是说，一个 Profile 可以拥有自己的模型选择。

例如：

```
default
→ free model

coder
→ coding model

quant
→ research model
```

这为以后根据任务类型选择模型提供了基础。

# 十五、Session、Profile、Skills 的区别

今天把三个概念重新进行了区分：

### Session

解决：

> **这一次任务做到哪里了？**

### Profile

解决：

> **这个 Agent 平时以什么环境和配置工作？**

### Skill

解决：

> **这个 Agent 做某一类任务时，应该遵循什么流程？**

可以简单记成：

```
Profile
= Agent 的工作环境

Session
= Agent 的一次工作过程

Skill
= Agent 的专业工作方法
```

三者结合后，一个 Agent 系统才开始真正变得可管理。
