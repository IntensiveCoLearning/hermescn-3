# 2026-09-03

# 9/3 Day 1：安装并完成第一次对话（环境验证与 doctor 诊断）

### 1. Hermes Agent 是什么

 

Hermes 不只是聊天机器人或代码补全工具，而是能够**理解目标 → 调用工具 → 执行动作 → 观察结果 → 再决定下一步**的 Agent。

它可以操作文件、执行终端命令、访问网页、使用外部服务、保存 Memory / Skills，并通过 Gateway 接入消息平台。模型负责“判断”，工具负责“行动”。

一个简单判断标准：

> **固定规则、固定输入、固定输出 → 脚本更合适。**\
> **需要阅读、判断、多步骤操作和动态决策 → Agent 更有价值。**

适合 Hermes 的任务通常应该具备：

**目标 → 输入 → 权限范围 → 验收标准**

如果这四个东西说不清楚，不应该直接让 Agent 开始工作。

### 2. 安装与第一次运行

 

Hermes 有 **Desktop / CLI** 两种主要入口，本质上使用的是同一个 Agent 核心。我选择了 Desktop。\
![image.png](https://cdn.intensivecolearn.ing/images/programs/cmtfruwwx1ev1ro29dtsjp8v6/checkins/icl1-user-3427329/2026-09/6bf92165-d191-498f-843a-9119932a4c70.png)

### 3. 第一个真实任务：从“聊天”进入“执行”

 

第一个任务的重点不是生成一篇漂亮的 `summary.md`，而是第一次完整经历：

**读取输入 → 理解任务 → 使用工具 → 创建文件 → 检查结果 → 人工验收**

练习在独立的 `hermes-first-task` 目录中进行

一个好的 Agent Prompt 至少包含：

Input：允许读取哪些文件\
Goal：最终需要产生什么\
Structure：输出应该包含什么\
Constraints：哪些事情不能做\
Approval：哪些动作需要先询问\
Acceptance：怎样判断任务完成

例如：

> 只读取指定文件，不联网、不修改原文件，只创建 `summary.md`，完成后检查文件是否存在并核对内容。

这实际上是以后设计 Agent Workflow 最重要的基础模式。

### 4. Hermes 是如何工作的

 

可以把 Hermes 的核心执行模型理解成：

```
User Goal
   ↓
Context
   ↓
Model 判断下一步
   ↓
Tool 执行动作
   ↓
Tool 返回结果
   ↓
Model 再判断
   ↓
继续执行 / 请求人工确认 / 完成
```

这里有三个非常关键的认知：

**第一，模型 ≠ 工具。**\
&#x20;模型本身不能直接读取你的文件或修改电脑，它必须通过工具完成真实操作。

**第二，工具执行成功 ≠ 任务成功。**\
 例如命令返回 `exit code 0`，只代表命令执行成功，不代表业务结果正确；文件存在，也不代表内容正确。

**第三，Permission ≠ Validation。**\
&#x20;“允许 Agent 做这个动作”和“Agent 做出来的结果正确”是两件完全不同的事情。最终仍然需要验收。

因此一个可靠的 Agent Workflow 应该是：

> **Action → Observe → Validate**

而不是：

> **Action → Done**

### 5. 权限、安全与凭据

 

Hermes 的安全原则不是“一律禁止”，而是：

> **权限、操作范围和潜在后果必须匹配。**

每次批准一个动作，可以问自己五个问题：

1. 它会接触什么？
2. 它会改变什么？
3. 能不能恢复？
4. 结果会不会离开本机？
5. 是否涉及凭据、资金或生产系统？

风险大致从：

**读取指定文件 → 创建文件 → 覆盖文件 → 网络访问 → 删除 / 发布 / 生产环境 → 支付 / 转账 → 凭据泄露**

逐渐升高。

特别需要记住：

**API Key、OAuth Token、GitHub Token、云服务密钥、钱包私钥/助记词都属于凭据。**

不要把它们放进 Prompt、截图、Git、Issue 或聊天记录中。优先使用 OAuth 或 Hermes 的 credential management。

# 2026-09-06

# 9/6 Day4：**定时任务 和多媒体输入**

### **Cron 定时任务**

**核心概念**：Cron job 在每个 **fresh session（新会话）** 中运行，不记得创建时的上下文。因此 prompt 必须**自包含**——写清身份、行为边界和输出格式，不能出现"刚才那个东西"这类模糊指代。

**输出位置**：`$HOME/.hermes/cron/output/<job_id>/`

**关键认知**：

* 每次运行都调用模型 → 有 token 成本；忘记删除的重复任务会持续烧钱
* 交付到飞书前必须先验证 home channel 配置
* 故障排查顺序：`gateway status --deep` → `cron status` → `cron list --all` → 检查时区/凭据/模型
* 有固定输出的脚本类任务可考虑 **no-agent 模式**（免 LLM 成本）

### **语音、图片、文件输入**

**处理链路**：飞书上传 → Gateway 下载到本地缓存 → 工具/模型处理 → 回复

**隐私边界**（重要）：语音/图片/文档在**飞书服务端、Gateway 运行机器、云端 STT/Vision 服务**三处都可能形成副本。删除飞书消息 ≠ 清除所有缓存。决定"能不能发"前，先判断数据是否允许进入每一段链路。

**前置条件**：

* 飞书应用必须具备 `im:resource` 权限（访问用户发送的图片、文件、音频）
* 权限修改后需发布新版本 + 企业审批

**故障排查顺序**：

* 全部失败 → 检查 Gateway 状态 + 普通文字回复是否正常 + `im:resource` 权限
* 仅语音失败 → 检查音频格式/STT 依赖/首次模型下载
* 仅截图失败 → 确认附件已下载 + 裁剪放大重试
* 仅文件失败 → 先用 `.txt` 排除格式问题
* 回复发不回来 → 问题在交付段而非识别段

***

**总结**：Cron 的核心是"自包含 prompt + 成本意识 + 完整生命周期管理"；多媒体的核心是"逐项验证处理链 + 明确隐私边界 + 失败时代替猜测"。两个教程都强调：**先本地练熟，再接入真实外发。**

# 2026-09-07

# 9/7 Day5：扩展与协作

今天三个主题实际上解决的是一个问题：当单个 Hermes Agent 开始变复杂后，如何进行任务分工、身份隔离和能力扩展。可以把它们理解为三个层次：**Delegation 解决“谁来做” → Profiles 解决“以谁的身份做” → Tool / Skill / MCP / Plugin 解决“用什么能力做”。** 

#### 1. Delegation：把任务交给子代理

Delegation 的核心不是“多开几个 Agent”，而是把**相互独立、可以并行完成的子问题**交给 Subagent，然后由 Parent Agent 最终汇总和验收。

最重要的认知是：Subagent 没有父 Agent 的完整上下文。它只知道 Delegation 时传入的 `goal` 和 `context`，因此任务必须明确写出：目标、资料来源、限制条件、输出格式、截止范围以及失败处理方式。

适合 Delegation：

* 多个互不依赖的研究任务
* 大型代码 Review
* 不同角度的独立分析
* 可以并行执行的资料整理

不适合：

* 严格前后依赖的任务
* 简单的一次工具调用
* 确定性的脚本处理
* 需要不断向用户提问的任务

###### 最重要的原则

> **Subagent 负责执行，Parent Agent 负责判断和验收。**

不能因为两个 Subagent 得出了相同结论，就认为结论一定正确。最终仍然需要回到原始资料、文件、测试结果等真实证据进行验证。并发越高，模型成本、请求压力和潜在副作用也会同步增加。

***

#### 2. Profiles：隔离 Agent 的身份和状态

Profile 可以理解为 Hermes 的**独立 Agent 身份空间**。

一个 Profile 可以拥有独立的：

**配置 / Credentials / Sessions / Memory / Skills / Cron / Logs**

因此可以建立：

```
```

```
default
├── 日常个人 Agent

work
├── 工作项目 Agent

research
├── 技术研究 Agent

bot
└── 特定机器人 Agent
```

这样做的核心价值不是“多开几个窗口”，而是避免不同用途之间的**上下文、配置、凭据和长期状态互相污染**。

特别需要注意：

> **Profile ≠ Sandbox**

这是今天非常重要的一个知识点。

Profile 可以隔离 Hermes 自身的状态，但并不会自动限制操作系统层面的文件访问权限。`terminal.cwd` 只是指定工具默认从哪里开始工作，并不能阻止 Agent 访问其他目录；真正的强制访问边界需要 Sandbox 等机制。

另外，创建新 Profile 时不要随便使用 `--clone`。Clone 可能复制原 Profile 的 `.env`、配置和 Skills，从而把原来的 API Key 或机器人凭据带到新的身份中。

#### 3. Tool / Skill / MCP / Plugin：到底怎么扩展 Hermes？

这一部分可以建立一个非常实用的判断模型：

| 扩展方式       | 核心作用                     | 适合解决什么               |
| :--------- | :----------------------- | :------------------- |
| **Tool**   | 给 Agent 一个具体能力           | “让它能够做 X”            |
| **Skill**  | 给 Agent 一套知识 + 方法 + 工作流程 | “让它知道应该怎么做 X”        |
| **MCP**    | 接入外部工具 / 数据 / 服务         | “让它能够连接外部系统”         |
| **Plugin** | 更完整的扩展/集成机制              | “让 Hermes 获得一整套外部能力” |

最容易混淆的是 **Tool 和 Skill**：

**Tool 是能力，Skill 是方法。**

例如：

> Tool：可以执行 SQL。\
> &#x20;Skill：告诉 Agent 如何安全地分析 PostgreSQL、先查询再修改、如何验证结果。

所以，如果只是缺少一个动作能力，优先考虑 Tool；如果 Agent 已经有工具，但**不知道专业领域的正确工作方法**，Skill 更合适。

而 MCP 的价值在于把外部系统能力标准化地提供给 Agent，例如数据库、第三方 API、企业系统等。

***

#### 今天最重要的 6 个 Takeaways

**① Delegation 是“任务级并行”。**

**② Profile 是“身份级隔离”。**

**③ Tool 是“能力”，Skill 是“方法”。**

**④ MCP 是连接外部工具和数据系统的重要标准化接口。**

**⑤ Profile 隔离 Hermes 状态，但不等于操作系统 Sandbox。**

**⑥ Agent 越复杂，越应该把“执行”和“验收”分开。**

# 2026-09-08

# 9/8 Day6：案列学习

今天两个案例真正要学习的不是“怎么做一个研究摘要”或“怎么配置 Cron”，而是把前两天的 Agent 能力进一步变成一个可验证、可恢复、可自动运行、可控成本的 Agent Workflow。\
核心闭环可以浓缩成：\
**Input → Change Detection → Agent → Artifact → Automated Validation → Human Verification → Delivery**

意味着 Hermes 开始从“会执行任务的 Agent”进入“可以稳定运行的 Agent System”。

##### 1. 可验证研究：不要相信 Agent 的“完成”

第一个练习**整理一组可验证资料**最重要的思想是 **Acceptance ≠ Tool Success**。

Agent 成功创建 `research-summary.md`，并不意味着研究结果正确。案例通过 Fixture + Source Label + Hash + Verification Script + 人工核对 建立证据链：

```
固定输入
  ↓
Hash 验证输入没被修改
  ↓
Agent 整理资料
  ↓
每条事实标注 Source
  ↓
自动检查格式、章节、来源
  ↓
人工检查事实、冲突、未知状态
```

尤其值得记住的是：**冲突不能由 Agent 擅自“解决”**。例如两个来源给出不同预算数字，正确做法是保留冲突并标明来源，而不是让模型自行选择一个看起来更合理的数字。 

这实际上是研究型 Agent 最重要的原则：

> **Agent 可以整理信息，但不能偷偷改变信息的不确定性。**

***

##### 2. Source / State / Evidence：研究结果必须可追溯

今天进一步理解了一个很重要的概念：**研究产物不是普通文本，而应该是一种带 Evidence 的 Artifact。**

至少需要区分：

**已确认事实 / 建议 / 未确认 / 信息缺口 / 冲突**

不能把：

> “有人建议这样做”

自动变成：

> “已经决定这样做”。

同样，缺失的数据不能让 LLM 根据上下文“补全”。这就是为什么案例要求保留负责人、日期、数字、时区以及未知状态。 

因此以后设计 Research Skill 时，可以把：

**Source → Claim → Evidence → Confidence → Conflict**

作为基本数据结构思考，而不是单纯要求 Agent “总结一下”。

***

##### 3. Daily Research Assistant：从一次性任务进入持续运行

第二个练习进一步把上述方法变成每日自动化：

```
Cron
 ↓
Pre-check Gate
 ↓
有没有变化？
 ├─ No → 不调用模型
 └─ Yes
      ↓
   Fresh Agent Session
      ↓
   读取资料
      ↓
   生成 daily-brief.md
      ↓
   自动验收
      ↓
   Delivery → 飞书
```

这里最值得学习的是 **Pre-check Gate**。

如果每天资料没有变化，就根本不应该唤醒 LLM。这样可以同时降低：

**Token 成本 + 模型调用次数 + Agent 风险 + 无意义执行。**

案例明确要求 `wakeAgent: false` 时跳过 Agent，而不是把“没有变化”理解成任务失败。 

***

##### 4. Fresh Session：自动化 Agent 不能依赖聊天记忆

Cron 每次运行都是新的 Session，因此 Prompt 必须 **Self-contained**。

也就是说：**不能假设 Agent 记得昨天发生了什么。**

需要让任务本身包含：

**输入位置 + 任务目标 + 输出位置 + 判断规则 + 限制条件 + 验收要求。**

这和我们之前学习的 Profile / Delegation 其实是连起来的：**Agent System 越自动化，就越不能依赖隐式上下文。**

***

##### 5. 今天最重要的工程思想：Gate + Artifact + Acceptance

我认为今天最值得记住的是这三个概念：

###### Gate：要不要让 Agent 工作？

通过变化检测、条件判断、权限检查决定是否唤醒模型。

###### Artifact：Agent 到底产生了什么？

例如：

```
research-summary.md
daily-brief.md
verification result
execution log
```

Agent 的价值应该最终沉淀为**可检查的产物**，而不是停留在聊天窗口。

###### Acceptance：产物真的合格吗？

自动脚本检查结构、文件、Hash、来源等；人工检查语义、事实、冲突和判断。

所以完整闭环应该是：**Trigger ≠ Execution ≠ Success**

真正的 Success 是：**Trigger → Execution → Artifact → Validation → Delivery**
