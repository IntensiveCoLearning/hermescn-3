# **Hermes Agent 使用指南（越用越聪明的 Agent）**

> 生成时间：2026-09-01\
> 这份指南基于 **Hermes Agent v0.20.6**（Nous Research 出品）的已安装源码（`Lib\site-packages\`）和你本机 `~/.hermes/` 目录的真实状态写成。\
> ✅ = 从源码/本机文件核实 ✅；❓ = 推测/未核实 ❓（见文末"可信度说明"）。

***

## **0. 一句话定位**

**Hermes 是一个"会学习的终端 Agent"**：模型可以换成便宜的（你本机就配的是 `deepseek-chat`），然后用三样东西补偿模型的智商——

1. **记忆**：记住关于你的事实，跨会话
2. **技能**：把做过的活变成可复用的 skill，越用越熟
3. **每轮后台自省**：每次对话结束，一个后台分身自动回顾"这轮值不值得记住/升级技能"

核心卖点：**你用得越多，它越懂你的工作方式** —— 这是它和 Claude Code 最本质的区别。

## **3. 核心机制拆解：它到底怎么"越用越聪明"**

### **3.1 每轮对话结束后的"自省分身"（最关键）✅**

源码 `agent/background_review.py` 写得很清楚：

```
```

```
你发消息 → 主 Agent 回答 → 主 Agent 悄悄启动一个后台守护线程 fork
   ↓
fork 重放这轮对话的快照，问自己一个问题：
  "这一轮对话，有没有值得 ①存进记忆 或 ②改进技能 的东西？"
   ↓
有 → 直接写入 memories/ 或 skills/（受审批门约束，见 3.4）
```

几个关键设计（都是源码确认的）：

* **fork 继承主 Agent 的全部运行时**（同一个模型、同一套密钥、同一份缓存系统提示）→ 命中前缀缓存，成本很低
* **fork 的工具白名单只有记忆 + 技能管理**，其他工具全部运行时拒绝 ✅ → 它**只负责学习，永远碰不到你的执行操作**，这是安全设计
* 每轮最多 fork 一次，输入预算默认上限 60 万 token（`max_input_tokens`），防止失控
* 主开关：`background_review.enabled`（默认 **true**）

**给你的实用建议**：如果你想省钱，可以把 review fork 路由到更便宜的模型（`background_review.provider/model`），官方注释说质量基本不降 ✅。

<br />

打开后用法：`/memory pending` 看待审批 → `/memory approve <id>` / `/memory reject <id>`。技能侧对应 `/skills pending`、`/skills approve`、`/skills diff <id>`、`/skills reject`。

**给你的建议**：先开着审批门用一段时间，看看它都学什么，再决定是否全自动。

### **3.5 手动触发自省：`/refine` ✅**

不想等每轮自动 fork？聊完一长段后敲 `/refine`，立即对当前会话跑一次记忆/技能 review，可带焦点：`/refine 记住用户用中文名交流`。

### **3.6 Journey 图谱：把你的"成长"可视化 ✅**

* CLI：`hermes journey`（时间线柱状图）
* 对话内：`/journey`（TUI overlay）
* 桌面版：Star Map / 记忆图谱

图谱节点 = 你学会的技能 + 记忆条目，按时间排列。技能间靠 `related_skills` 字段连边，记忆和技能靠词面重叠连边。可以 `hermes journey delete|edit` 手动修正它学错的东西。✅

## **工作流推荐：怎么让它"越用越聪明"**

### **三周养成法**

**第 1 周：喂模式**

* 把所有**你会重复做 2 次以上**的活都丢给它做（文档转格式、批量重命名、表格清洗…）
* 聊完一段就 `/refine`，让学习立即发生
* 打开审批门，每天 `/memory pending` + `/skills pending` 看它学了什么，`reject` 学错的

**第 2 周：固化**

* 看到它反复做对一件事，敲 `/learn`（无参 = 从当前对话学），把它固化成正式技能
* 用 `/skills diff <id>` 检查它写的技能对不对（`author` 是不是 Hermes？`description` 有没有超 60 字符？）
* `hermes journey` 每周看一次你的"技能增长曲线"

**第 3 周：调优**

* 把 `write_approval` 关掉，让它全自动学习（你已经信任它了）
* 把学歪的技能 `hermes journey delete` 删掉
* 技能多了以后用 `related_skills` 建立关联，图谱更清晰

# 2026-09-06

将模糊需求转成 Hermes 可理解的执行任务，核心方法是**用"背景-目标-约束-验收标准"四要素把抽象意图还原成可分解、可执行、可验证的结构化指令**，而非依赖 Agent 自己去"猜"。Hermes 虽然具备智能任务拆解能力（会自动把复合指令解析为带依赖关系的子任务图谱），但拆解质量高度取决于你输入的结构化程度——信息越完整，子任务拆分越精准，幻觉和返工越少

## 一、为什么模糊指令在 Hermes 上会失效

Hermes 解析一条指令时，会按"动词主干 + 对象实体 + 时序要求 + 输出格式约束"四个维度做语义原子化切分，再映射到已注册工具的能力边界。当输入缺少其中任何一项，它就会退化为两种典型失败模式：

* **抽象动词无锚点**：像"优化一下"“分析下”"整理一下"这类动词，没有可执行的对象和动作边界，Hermes 会随机选择策略，导致输出不稳。
* **缺少验收标准**：没有明确的完成标志和证据要求，Hermes 容易"表面完成"——说做完了但文件没生成、推送没发出去

实测数据显示，缺少约束的裸指令达标率约 94.1%，而带结构化约束的指令可达 100%，且 token 成本反而更低（1.44× vs 2.28×）——因为 Agent 不需要反复试探

## 二、模糊 vs 结构化指令对照

| **维度**   | **模糊指令示例** | **结构化改写示例**                                                         |
| :------- | :--------- | :------------------------------------------------------------------ |
| **目标**   | “帮我做个数据分析” | “基于 /data/sales\_2026Q2.csv，统计各区域月度销售额并输出趋势结论”                      |
| **输入**   | 未指定        | 明确文件路径 / API 地址 / 上下文来源                                             |
| **输出格式** | 未指定        | “输出 Markdown 表格，含列名：区域、1-6月销售额、环比增速；末尾附 3 条结论”                      |
| **工具权限** | 未指定        | “允许调用 pandas 和 matplotlib；如需联网请先告知”                                 |
| **边界条件** | 未指定        | “数据缺失时不要填充，标记为 N/A 并在结论中说明”                                         |
| **验收标准** | 未指定        | “交付物：./output/q2\_report.md + ./output/chart.png，且图表必须包含所有 6 个月数据点” |

## 五、不同复杂度任务的写法差异

**简单查询类**（一次性、单步）——四要素可以精简为"目标 + 输出格式"两要素，无需复杂的验收标准。例如：“搜索 2026 年 AI Agent 市场规模，返回 3 条数据来源链接”。

**多步执行类**（跨工具、需拆解）——必须显式使用 `/goal` 或 `/plan` 命令触发任务拆解机制。`/goal` 会自动把目标拆成子任务并逐项自检，`/plan` 则只生成执行路径让你确认后再跑**php.cn+1**。此类任务必须写清"验收标准"和"失败处理"，否则中间步骤断裂时 Hermes 不会主动兜底。

**需人工确认类**（高风险、不可逆操作）——在指令中显式加入"操作前先问我确认"，并指定哪些动作属于需审批的范畴。例如删除文件、发送对外邮件、修改生产环境配置等，Hermes 默认有危险命令确认机制，但显式声明能进一步降低误操作风险**tencent.com+1**。

## 六、三个高频踩坑点

* **只用抽象动词，不给动作边界**：“优化下这段代码"应改为"将 `process_data()` 函数的循环复杂度从 O(n²) 降到 O(n log n)，并补充 3 个单元测试用例”。
* **缺少输出格式锚点**：不指定格式时，Hermes 可能在同一对话里输出纯文本、JSON、表格混杂的结果。把 `<output_schema></output_schema>` 或明确的字段清单写进指令，能强制模型按结构返回**php.cn**。
* **约束堆砌过载**：实测数据显示，把身份、项目、记忆、输出格式四层约束全部叠加，token 成本飙到 2.66×，达标率反而从 100% 跌到 96.1%——注意力被稀释了。**1-2 层结构化约束是甜点区**（1.4-1.7× 成本、100% 达标），行为纪律放 SOUL.md，项目规则放 AGENTS.md，临时任务信息放当次指令即可，不要全部塞进一条 prompt**csdn.net+1**。

一条实用的自查口诀：**交付物是什么、用什么格式、证据在哪里、失败了怎么办**——这四问都能在你的指令里找到答案，Hermes 就能稳定执行；任何一问含糊，它就会开始"自由发挥"。

# 2026-09-08

Hermes Agent 的多 Agent 管理核心是"**Profile 做角色隔离、Session 做上下文载体、四种协作模式（Profile / delegate\_task / Kanban / 外部集成）按任务耦合度分层选择**"——Profile 提供每个 Agent 独立的配置、记忆、会话与状态数据库，Session 负责承载与续接对话上下文，而多 Agent 之间的协作则根据任务是否需要持久化、是否跨进程、是否有人类介入来选择不同原语**。**

## 一、Hermes Profile 的本质：一个 Agent 就是一个独立的 HOME 目录

Profile 不是简单的"配置切换器"，它是一份完全独立的 Hermes 状态目录。每个 Profile 拥有自己的：

* `config.yaml`（模型、provider、工具集、所有设置）
* `.env`（API Key、各平台 Bot Token）
* `SOUL.md`（人格与指令，即 system prompt）
* `memories/`（长期记忆）、`sessions/`（历史会话）
* `skills/`、`cron/`、`plugins/`、`state.db`（状态数据库与网关状态）**csdn.net+1**

默认 Profile 位于 `~/.hermes/`，其他 Profile 通常位于 `~/.hermes/profiles/<name>/`。创建一个 Profile 后，它会自动成为一条独立命令：

**bash**

复制

```
hermes profile create coder          # 创建 + 生成 "coder" 命令别名
coder setup                          # 配置 API Key 与模型
coder chat                           # 直接进入该 Profile 的聊天
coder config set terminal.cwd /abs/path/project  # 绑定默认工作目录

```

<br />

**引用**

**三条关键约束需要特别注意**：

1. **绝不让两个 Agent 进程指向同一个 Profile**。两个进程都会自动写记忆，并在 session 启动时互相加载对方的写入，最终状态会互相污染到完全失控。需要共享记忆的 Agent 应使用外部记忆 provider（如 Honcho）。
2. **Profile 不是沙盒**。Profile 只隔离"状态目录"，不隔离文件系统访问。默认 local 终端后端下，Agent 仍拥有你用户账户的全部文件访问权限。要限制访问范围，需在 config 中显式设置 `terminal.cwd`，或使用沙盒后端。
3. **`SOUL.md` 修改只在新 session 干净生效**，旧 session 可能仍在使用修改前的 prompt 状态。

OAuth 登录（Claude Pro/Max、OpenAI Codex、xAI）使用单次刷新 token，`--clone-all` 会跳过这些行——新 Profile 继续从根目录 `~/.hermes/auth.json` 读取登录态，任意 Profile 刷新 token 都会写回根目录，保证所有 Profile 保持登录。

## 二、Session 管理机制：对话即持久化实体

Hermes 将**每一场对话**——无论是 CLI、Telegram、Discord、Slack、WhatsApp、Matrix 还是其他 15+ 平台——都自动存为一个 session，记录在 `~/.hermes/state.db`（SQLite + FTS5 全文检索）。

数据库中每个 session 记录：Session ID、来源平台、用户 ID、唯一人类可读标题、模型与配置、system prompt 快照、完整消息历史（含 tool calls 与结果）、token 计数、时间戳，以及 `parent_session_id`（用于压缩触发的 session 分裂谱系）。

### Session 的关键行为

* **上下文管理**：Hermes 不会把历史所有字节反复塞回 prompt。每轮模型只看到 system prompt、当前对话窗口和该轮显式注入的内容。媒体附件按"turn-scoped"处理——原始图片/音频字节不会复制进后续轮次，只有描述、路径或最终回复会保留。
* **压缩与谱系**：session 变长时用 `/compress` 压缩，或 `/new` 开新线程。压缩会自动创建一个 continuation session，原 session 标题会自动编号：`"my project" → "my project #2"`。`hermes -c "my project"` 会自动恢复谱系中最新的那个。
* **跨平台无缝迁移**：在 CLI session 里执行 `/handoff telegram`，gateway 会将 live conversation 完整转移到 Telegram 的新 topic/thread，session ID 不变、完整 role-aware transcript 保留，agent 从 CLI 停下的位置继续。回到 CLI 只需 `/resume <title>`。
* **恢复与工作区**：`hermes -c` 恢复最近 session，`hermes -c "名称"` 按标题恢复，`hermes -r <session-id>` 按 ID 恢复。恢复时会自动 `cd` 回 session 记录的工作目录（git repo 根或项目目录），也可用 `--no-restore-cwd` 保持在当前目录。
* **按工作区过滤**：`hermes sessions list --workspace my-project` 只显示属于某个 git repo/目录的 。

每个 Profile 拥有**自己独立的 sessions 历史与 state.db**，这是 Profile 隔离的核心之一——一个 Agent 的对话不会出现在另一个 Agent 的 session 列表里。

## 三、多 Agent 协作模式：四种原语的适用边界

Hermes 提供至少四种协作模式，核心选择标准是**任务耦合度**——越松散越适合重隔离，越紧密越适合轻量委派。

| **维度**   | **Profile 分身**                       | **delegate\_task 委派**    | **Kanban 看板**                 | **外部框架集成**               |
| :------- | :----------------------------------- | :----------------------- | :---------------------------- | :----------------------- |
| **形态**   | 独立进程 + 独立 HOME                       | 同进程内临时子 Agent            | SQLite 持久化任务板                 | 跨框架 API/事件总线             |
| **上下文**  | 完全隔离（各自 sessions/memory）             | 子 Agent 独立上下文，只回传摘要给父    | 卡片携带完整上下文，comment 是 Agent 间协议 | 取决于外部协议                  |
| **生命周期** | 永久（systemd/s6 服务）                    | session 内（session 关闭即终止） | 跨重启持久（SQLite 行永远存在）           | 跨系统                      |
| **协作方式** | 各自独立运行                               | 父 → 子单向 RPC（fork → join） | 任意 Profile 读写任意任务，peer 协作     | 松耦合事件驱动                  |
| **适用场景** | 长期角色定义（coder/researcher/writer 各自人设） | 短任务委派、并行推理、上下文隔离         | 跨 Agent 边界、需人类介入、需审计轨迹        | 与 LangGraph/CrewAI 等编排集成 |
| **不适用**  | 需要频繁跨 Agent 传递上下文                    | 长周期任务、需要人工 review        | 单次简单子任务                       | 紧耦合实时协作                  |
